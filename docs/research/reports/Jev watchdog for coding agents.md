# Make Jev Judge Progress, Not Activity

Jev's proposed defaults are close, but they mix up two questions: is a session alive, and is it moving forward? Keep the 20-minute silence rule and the "one bad scan is a warning, two in a row is stuck" debounce. Measure silence only on the agent loop's own trace events, not on harness heartbeats. Pause the clock while a tool call is still inside its own timeout. Add a separate, longer window, about 60 minutes, for durable progress: a pushed commit, a checkpoint, or a test that starts passing. That margin is needed because Anthropic measured 99.9th-percentile Claude Code turns at more than 45 minutes. Replace "the same action 3 times" with fingerprinted rules taken from OpenHands: 3 identical action-error pairs earn a nudge, 4 mean stuck, and 4 identical action-observation pairs or 6 A/B alternations also mean stuck. Demote "5 failing commands per scan" to a supporting signal, because no source shows raw failure counts predict stalls. On Gitea 28.2, the CI verdict comes from `GET /repos/{owner}/{repo}/commits/{sha}/status?limit=50`. The combined state in that response covers only the returned page, and Gitea records cancelled runs as `failure`, so the "3 failing commits" rule needs filtering before Jev can trust it. The issue-labels endpoint accepts integer IDs or string names, never mixed, and has since v1.22. It silently drops unknown names, and removing a single label takes only an ID, so Jev should work in IDs. Stopping is a ladder that Jev proposes and a policy owner carries out: a cooperative stop request, a grace window of about one scan for a WIP commit, checkpoint and lease release, then a hard stop backed by lease expiry and an epoch fence. Escalation stays quiet when every comment is keyed to its stall episode and edited in place. A human is paged only when the Lead fails to act or a restart circuit breaker opens.

## Two clocks and a fingerprint beat five flat rules

Jev scans every 10 minutes. Each of its five proposed rules is one way of answering "is this session stuck?" The evidence says it should answer three narrower questions. Is the agent loop alive? Is the work advancing? Is the agent repeating itself? Production systems keep these apart. A Kubernetes liveness probe restarts a container after `failureThreshold` (default **3**) consecutive failures at a 10-second period ([kubernetes/api types.go](https://github.com/kubernetes/api/blob/master/core/v1/types.go)). A Deployment's separate `progressDeadlineSeconds`, **default 600**, measures whether the rollout itself has advanced. When it expires, Kubernetes only *reports* `ProgressDeadlineExceeded` and leaves the action to "higher level orchestrators" ([Kubernetes: Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#progress-deadline-seconds)). Temporal states the principle directly: heartbeating "is best thought about not in terms of time, but in terms of 'How do you know you are making progress?'" ([Temporal: Detecting Activity failures](https://docs.temporal.io/encyclopedia/detecting-activity-failures)).

### Silence catches hangs, but only durable artifacts prove progress

The proposed hung rule, "no output, trace or commit for 20 minutes", is really a liveness check. Output is the most frequent of the three signals, so it nearly always decides the outcome. That makes the rule easy to defeat. GitLab drops jobs that print nothing for an hour, and its documented workaround is to "add a script to continuously output progress" ([GitLab Docs: pipeline settings](https://docs.gitlab.com/ci/pipelines/settings/#set-a-limit-for-how-long-jobs-can-run)). Output keeps a job alive. It does not show the job is getting anywhere. A looping agent produces plenty of output and passes this rule forever. The same holds for lease heartbeats sent by the harness: they prove the process is up, not that the model is doing useful work. Jev should therefore tell apart three states that the proposal lumps together. A session is **dead** when its lease heartbeat has gone stale; lease expiry already handles that. It is **hung** when the heartbeat is fresh but the agent loop has logged no model response or tool event. It is **spinning** when the loop is active but nothing durable has changed.

For the hung check, 20 minutes is generous next to infrastructure defaults: CircleCI's `no_output_timeout` is **10 minutes** ([CircleCI configuration reference](https://circleci.com/docs/reference/configuration-reference/)), and Airflow fails a task whose heartbeat is older than **300 s** ([Airflow config.yml](https://github.com/apache/airflow/blob/main/airflow-core/src/airflow/config_templates/config.yml)). The generosity is the right choice for Jev, though. A timeout has to exceed the sampling interval by a margin; Temporal throttles heartbeats to 0.8× the timeout for that reason ([Temporal](https://docs.temporal.io/encyclopedia/detecting-activity-failures)). A 20-minute window sampled every 10 minutes keeps that margin. Three exclusions keep the rule honest. The first is a tool call still running inside its own timeout. SWE-agent bounds each command at **30 s**, caps total execution at **1,800 s**, and exits after **3 consecutive** command timeouts ([SWE-agent tools.py](https://github.com/SWE-agent/SWE-agent/blob/main/sweagent/tools/tools.py); [agents.py](https://github.com/SWE-agent/SWE-agent/blob/main/sweagent/agent/agents.py)). A long build should be bounded by its own timer like this, not by the session's stall clock. The second is session startup. Kubernetes added startup probes so that slow initialisation does not force a loose liveness probe; its documented example allows 30 × 10 s before liveness takes over ([Kubernetes probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/#define-startup-probes)). Clone, dependency install and context loading deserve the same grace. The third is an agent that has stopped to ask a question. It is healthy, not hung: on the most complex tasks, "Claude Code stops to ask for clarification more than twice as often as humans interrupt it" ([Anthropic: Measuring agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy)).

Progress needs its own, longer window based on durable artifacts. Ranked from strongest to weakest, the signals are: a test or feature flag that flips from failing to passing, a pushed commit with a non-empty diff, a new checkpoint or decision trace, and a new *distinct* tool call. Anthropic's long-running harness uses exactly these artifacts: per-feature commits, a `claude-progress.txt` log, and a JSON feature list whose `passes` flags agents may flip but never edit away ([Anthropic: Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). The window has to clear legitimately long autonomous stretches. Between October 2025 and January 2026, the 99.9th-percentile Claude Code turn "nearly doubled, from under 25 minutes to over 45 minutes", while the median turn is about 45 seconds ([Anthropic](https://www.anthropic.com/research/measuring-agent-autonomy)). **Sixty minutes without durable progress** is a defensible starting point. It is still a local policy choice: no source publishes a commits-per-hour or tests-per-hour threshold for declaring a coding agent stuck. Jev should tune it per role from its own scan history, not treat it as settled.

### Loops need fingerprints of action and result, not action alone

"The same action 3 times in a row" fires on legitimate work. An agent chasing a flaky test reruns `pytest` three times and gets three different results. That is diagnosis, not a loop. OpenHands has the most explicit published detector, and it fingerprints the *pair*: the action together with its observation or error. Its `StuckDetectionThresholds` defaults are **4** identical action-observation pairs, **3** identical action-error pairs, **3** consecutive agent monologue messages, and **6** for A/B alternation ([OpenHands SDK types.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/types.py)). The detector scans only the last **20 events** since the last user message. It compares tool name, action content and thought, and ignores IDs and metrics. It also escalates in two steps. When an action-error streak first equals 3, it injects a nudge ("Repeating the exact same call again will not work"), and it declares the agent stuck only one repeat past that threshold ([OpenHands stuck_detector.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/stuck_detector.py)). Alternation gets a higher count because a two-state cycle such as edit, test, edit, test is normal. The number 3 recurs across tools for "the same failure again": Aider allows **3** reflections before "Only 3 reflections allowed, stopping" ([Aider base_coder.py](https://github.com/Aider-AI/aider/blob/main/aider/coders/base_coder.py)), and SWE-agent exits after 3 consecutive timeouts. Loops are worth this precision. In the MAST taxonomy, step repetition is reported as the most frequent multi-agent failure mode, at about 15.7% of 1,600+ annotated traces. That figure comes from secondary summaries and may differ between paper versions ([alphaXiv overview of arXiv 2503.13657](https://www.alphaxiv.org/overview/2503.13657)).

Jev should therefore hash `(tool, canonicalised arguments, observation-or-error)` for each event in that 20-event window and apply the OpenHands counts. The 10-minute cadence is the catch. A tight loop can repeat many times between scans, and every repeat costs tokens. The in-session detector belongs inside the session: the OpenHands SDK runs `stuck_detection = True` by default with a 500-iteration cap ([local_conversation.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py)), and a Claude Code hook can halt the loop with `{"continue": false, "stopReason": ...}` ([Claude Code: Hooks reference](https://code.claude.com/docs/en/hooks)). Jev is the backstop that also keeps the record. It catches what the in-session detector misses and writes down the pattern as evidence.

The "5 or more failing commands in one scan" rule should be demoted. Agents fail commands constantly while exploring: a `grep` with no match exits non-zero, and a test-first workflow starts with red tests. A looping agent, meanwhile, can succeed over and over at a no-op. Neither research thread found any source that evaluates tool-call failure rate as a predictor of being stuck. Every detector surveyed counts *repetition*, not volume. A raw failure count should therefore add to a bad scan only when the same scan also shows no durable progress. Its job as a standalone trigger goes to SWE-agent's sourced rule of 3 consecutive command timeouts.

### Gitea reports cancelled runs as failures, which skews the CI rule

"CI failing on 3 consecutive commits" fits the small-integer consensus above. On Gitea, though, it needs three corrections before it means anything. First, Gitea Actions maps a job's **Cancelled** status to commit status `failure` ([services/actions/commit_status.go](https://github.com/go-gitea/gitea/blob/v28.2.0/services/actions/commit_status.go#L373)). A run cancelled because a newer push superseded it therefore counts as a failure on the old SHA. An agent that pushes three commits in quick succession would trip the rule without a single real test failure. Second, a commit with zero statuses reports combined state `pending` with `total_count` 0 and `statuses: null` ([services/convert/status.go](https://github.com/go-gitea/gitea/blob/v28.2.0/services/convert/status.go#L46)). That means "no CI reported", not "CI running", and it should count neither for nor against the session. Third, the combine rule has changed between versions. Since v1.26, `warning` collapses to `failure` and `skipped` counts as success, so the combined state is only ever `pending`, `success` or `failure`. Before v1.25 the combined state could itself be `error` or `warning` ([commitstatus/commit_status.go v28.2.0](https://github.com/go-gitea/gitea/blob/v28.2.0/modules/commitstatus/commit_status.go#L67); [v1.24.0](https://github.com/go-gitea/gitea/blob/v1.24.0/modules/structs/commit_status.go)).

The corrected rule counts **3 consecutive head commits whose CI completed with a non-cancelled failure**, and resets on any success. For Gitea Actions, the run list's `conclusion` field (`success`, `cancelled`, `failure`, `skipped`) tells a cancellation apart from a real failure ([services/convert/convert.go](https://github.com/go-gitea/gitea/blob/v28.2.0/services/convert/convert.go#L445)). One refinement goes beyond what the sources say. A session that cuts five failing job contexts to two is converging, even though all three commits are red. Jev should therefore skip a commit whose set of failing contexts is strictly smaller than the previous one. WIP commits made during a stop grace window, described below, should be excluded the same way.

### Two consecutive scans confirm, and the first one should nudge

The proposed debounce, one bad scan for a warning and two consecutive for stuck, matches how mature systems trade detection speed for precision. Kubernetes needs 3 consecutive probe failures and only 1 success to recover ([types.go](https://github.com/kubernetes/api/blob/master/core/v1/types.go)). Prometheus holds an alert in "pending" until its `for` duration has elapsed, and uses `keep_firing_for` "to prevent situations such as flapping alerts" ([Prometheus: Alerting rules](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/)). SWE-agent resets its timeout counter whenever a command succeeds in between ([agents.py](https://github.com/SWE-agent/SWE-agent/blob/main/sweagent/agent/agents.py)). The Google SRE Workbook recommends pairing a long window with a short confirmation window ([SRE Workbook: Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/), secondary summary). Jev's threshold windows play the long-window role, and the second scan is the short confirmation.

Three changes make the debounce work. First, give the warning scan a job, borrowed from OpenHands' nudge-then-stuck sequence: the first bad scan posts an in-band nudge to the session, and the second bad scan escalates. Second, define a "good scan" as one with *durable* progress. Otherwise a chatty, looping session resets its own counter. Third, a scan that could not observe the session, because Gitea errored or the trace store was unreachable, is **unknown**, not good or bad. It leaves the counters untouched, in keeping with the constitution's rule that "not run" never means passed ([constitution Art. IV](../../../.specify/memory/constitution.md)). The latency trade-off is acceptable. Last activity at time *t* produces a warning between *t*+20 and *t*+30 minutes and a stuck verdict between *t*+30 and *t*+40. A hung session burns no tokens while it waits, so precision is worth more than speed there. Loops are the expensive failure, which is why their first line of defence lives inside the session. After a session recovers, Jev should keep the episode open for one more scan, the `keep_firing_for` pattern. A relapse inside that hold then reuses the same episode instead of starting a new escalation.

## Gitea 28.2 serves every verdict Jev needs, and the labels endpoint takes IDs or names

Every endpoint below was checked against the Gitea source at tag **v28.2.0**, the newest release on 2026-10-22. Version 28.0.0 dropped the leading "1." from Gitea's version numbers after 1.27 ([go-gitea/gitea tags](https://github.com/go-gitea/gitea/tags)). The REST base path is still `/api/v1`, and each instance serves its own authoritative spec at `GET /swagger.v1.json`. The hosted docs at docs.gitea.com could not be fetched during this research, so source code is the only reference. These are the calls Jev needs:

```http
# Start-up self-checks
GET    /api/v1/version                                         # branch on combine-rule history
GET    /api/v1/settings/api                                    # effective default_paging_num / max_response_items
GET    /api/v1/repos/{owner}/{repo}/branches/{default}         # refuse to run if user_can_push or user_can_merge is true

# CI verdict for a session branch
GET    /api/v1/repos/{owner}/{repo}/branches/{branch}          # commit.id = head SHA
GET    /api/v1/repos/{owner}/{repo}/commits/{sha}/status?limit=50
GET    /api/v1/repos/{owner}/{repo}/commits/{sha}/statuses?sort=highestindex&limit=50&page=N   # only if X-Total-Count > page
GET    /api/v1/repos/{owner}/{repo}/actions/runs?branch={branch}&limit=50                       # head_sha, status, conclusion
GET    /api/v1/repos/{owner}/{repo}/actions/runs/{run}/jobs

# Comments (issue or PR index)
GET    /api/v1/repos/{owner}/{repo}/issues/{index}/comments?since={RFC3339}
POST   /api/v1/repos/{owner}/{repo}/issues/{index}/comments    {"body": "..."}            -> 201 Comment
PATCH  /api/v1/repos/{owner}/{repo}/issues/comments/{id}       {"body": "..."}
GET    /api/v1/repos/{owner}/{repo}/issues/{index}/timeline                                # label and status events

# Labels
GET    /api/v1/repos/{owner}/{repo}/labels?limit=50&page=N     # repo labels only, no name filter
GET    /api/v1/orgs/{org}/labels?limit=50&page=N               # org labels (read:organization)
POST   /api/v1/repos/{owner}/{repo}/issues/{index}/labels      {"labels": [41]}           -> 200 []Label (full set)
DELETE /api/v1/repos/{owner}/{repo}/issues/{index}/labels/{id}                            -> 204 (integer ID only)
```

### One status call judges the head, if Jev checks the page size

`GET /commits/{ref}/status` (operationId `repoGetCombinedStatusByRef`) accepts a branch, tag or SHA. Branch names containing `/` work escaped or unescaped. `/statuses/{sha}`, by contrast, "only accepts commit ID" ([api.go](https://github.com/go-gitea/gitea/blob/v28.2.0/routers/api/v1/api.go#L1546)). Jev should read the head SHA from the branch first and then query by SHA, so the verdict is pinned to the exact commit it judged. The trap is paging. The handler computes the combined `state` over the returned page only, using a default of 30 contexts and a maximum of 50. The body's `total_count` is the length of that page; the true number of contexts is in the `X-Total-Count` header ([routers/api/v1/repo/status.go](https://github.com/go-gitea/gitea/blob/v28.2.0/routers/api/v1/repo/status.go#L254)). Only the latest status per context counts. When the header is larger than the page, Jev must read every page of `/statuses` and combine the results itself using Gitea's rule. That rule says: any `error`, `failure` or `warning` means failure; any `pending`, or no statuses at all, means pending; otherwise success, with `skipped` counted as success. Parsers also need to handle a JSON quirk that dates back to at least v1.22: an individual `CommitStatus` carries its state under the key **`status`**, while `CombinedStatus` uses **`state`** ([modules/structs/status.go](https://github.com/go-gitea/gitea/blob/v28.2.0/modules/structs/status.go#L13)). Gitea Actions jobs appear as contexts named `"<workflow> / <job> (<event>)"` with a target URL of `<run>/jobs/<id>` ([services/actions/commit_status.go](https://github.com/go-gitea/gitea/blob/v28.2.0/services/actions/commit_status.go#L158)), and all of these reads need only the `read:repository` scope ([api.go](https://github.com/go-gitea/gitea/blob/v28.2.0/routers/api/v1/api.go#L1611)).

### Comments never paginate, so upsert by marker

`GET /issues/{index}/comments` has **no `page` or `limit` parameters**. It returns every plain comment, oldest first, and accepts only `since` and `before` filters. Label and status events are left out; those come from `/timeline` ([routers/api/v1/repo/issue_comment.go](https://github.com/go-gitea/gitea/blob/v28.2.0/routers/api/v1/repo/issue_comment.go#L28)). `POST` takes exactly `{"body": "..."}` and returns 201 `Comment` with `id`, `body`, `user`, `html_url`, `created_at` and `updated_at`. It fails with 403, 404, or 423 when the repository is archived ([modules/structs/issue_comment.go](https://github.com/go-gitea/gitea/blob/v28.2.0/modules/structs/issue_comment.go#L37); [swagger](https://github.com/go-gitea/gitea/blob/v28.2.0/templates/swagger/v1-swagger.generated.json)). Both calls work on pull requests, because a PR's index is an issue index. Posting needs the `write:issue` token scope. Surprisingly, it needs only *read* permission on the Issues or Pull Requests unit, unless the issue is locked ([issue_comment.go](https://github.com/go-gitea/gitea/blob/v28.2.0/routers/api/v1/repo/issue_comment.go#L344)). The research could not confirm any `Idempotency-Key` header or conditional-write support on comments, so Jev should assume deduplication is its own job. The pattern is set out under escalation below.

### Labels accept IDs or names, never both, and removal takes only IDs

This answers the question directly. `IssueLabelsOption.labels` is typed `[]any`. The handler inspects each element by reflection: numbers are treated as IDs, strings as names, and anything else returns 400. A list that **mixes** IDs and names also returns 400, with "labels should be an array of strings or integers" ([routers/api/v1/repo/issue_label.go](https://github.com/go-gitea/gitea/blob/v28.2.0/routers/api/v1/repo/issue_label.go#L318)). Names have been accepted since **v1.22.0**, through PR #30943, backported as #30958 ([PR #30943](https://github.com/go-gitea/gitea/pull/30943)); v1.18 through v1.21 took IDs only ([v1.21.0 struct](https://github.com/go-gitea/gitea/blob/v1.21.0/modules/structs/issue_label.go)). Org-level labels have resolved by name since v1.23.0 ([v1.23.0 handler](https://github.com/go-gitea/gitea/blob/v1.23.0/routers/api/v1/repo/issue_label.go)). Names are still the riskier choice, for three reasons. Unknown names are **silently dropped**, because lookup is a plain `WHERE repo_id = ? AND name IN (...)` ([models/issues/label.go](https://github.com/go-gitea/gitea/blob/v28.2.0/models/issues/label.go#L374)). A name that exists at both repo and org level adds *both* labels. And `DELETE …/labels/{id}` takes only an int64. Jev should therefore build a name-to-ID map at start-up from `/repos/{o}/{r}/labels` and `/orgs/{org}/labels`, both paged at `limit=50`, add labels by ID, and confirm that the returned 200 list contains the IDs it expected. It should use `POST` (add), never `PUT` (replace), because PUT would remove labels set by people or other agents.

Labels themselves should be created once by a person. The label model has no unique index on name, so a bot's "create if missing" can race and produce duplicates ([models/issues/label.go](https://github.com/go-gitea/gitea/blob/v28.2.0/models/issues/label.go)). One Gitea feature fits Jev's state machine well. On an **exclusive** (scoped) label, adding `scope/x` removes any other label in the same scope from the issue ([models/issues/issue_label.go](https://github.com/go-gitea/gitea/blob/v28.2.0/models/issues/issue_label.go#L64)). If `jev/warning`, `jev/stuck` and `jev/parked` are created with `"exclusive": true`, each transition becomes a single idempotent `POST`. An issue never shows two contradictory verdicts at once.

### Least privilege needs an org team, not a collaborator grant

The token should carry `read:repository,write:issue`, plus `read:organization` if Jev reads org labels. Each write scope includes its read bit ([models/auth/access_token_scope.go](https://github.com/go-gitea/gitea/blob/v28.2.0/models/auth/access_token_scope.go#L56)). Scopes only cap what a token can do. What actually blocks push, merge and official approval is the account's repository permission. Labelling needs **write** on the Issues or Pull Requests unit, and without it the call returns 403 ([issue_label.go](https://github.com/go-gitea/gitea/blob/v28.2.0/routers/api/v1/repo/issue_label.go#L329)). A plain collaborator grant of `write` would also give write on Code. The clean setup is a 28.x **Bot**-type user, which cannot have a password or be site admin ([models/user/user.go](https://github.com/go-gitea/gitea/blob/v28.2.0/models/user/user.go#L977)), placed in an org team whose `units_map` is `repo.code: read`, `repo.issues: write`, `repo.pulls: write`, `repo.actions: read` ([modules/structs/org_team.go](https://github.com/go-gitea/gitea/blob/v28.2.0/modules/structs/org_team.go)). Jev can prove this separation instead of just asserting it. At start-up, `GET /branches/{default}` returns `user_can_push` and `user_can_merge` for the calling account ([repo_branch.go](https://github.com/go-gitea/gitea/blob/v28.2.0/modules/structs/repo_branch.go#L24)), and Jev should refuse to run if either is true. Two operational facts complete the picture. Gitea 28.2 has no built-in REST rate limiter, so Jev must throttle itself. Page sizes above 50 are silently clamped ([services/convert/utils.go](https://github.com/go-gitea/gitea/blob/v28.2.0/services/convert/utils.go#L15)). If Jev ever takes webhooks to trigger scans, `X-Gitea-Signature` is the bare lowercase hex of the body's HMAC-SHA256, with no `sha256=` prefix ([services/webhook/deliver.go](https://github.com/go-gitea/gitea/blob/v28.2.0/services/webhook/deliver.go#L94)).

## Jev proposes the stop; the policy owner carries it out

Kubernetes does nothing about a stalled Deployment beyond reporting a condition ([Kubernetes: Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#progress-deadline-seconds)). OWASP lists "excessive functionality; excessive permissions; excessive autonomy" as the root causes of excessive agency ([OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)). A watchdog that also fixes code and then decides whether the session is "unstuck" is grading its own work. Anthropic's harness had to design around exactly that self-certification failure ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Jev's write set should stay at its own comments and its `jev/*` labels. It *requests* a stop when a pre-declared policy rule allows; the Lead or a policy gate decides on and carries out a hard stop, as the constitution's "agents propose, policy decides" requires ([constitution Art. III](../../../.specify/memory/constitution.md)).

### A stop is a request, a grace window, then a hard kill

Mature runtimes stop work the same way. Kubernetes sends SIGTERM, waits `terminationGracePeriodSeconds` (**default 30 s**, with any `preStop` hook running inside that budget), then sends SIGKILL ([Kubernetes: Pod termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination)). Stock systemd waits **90 s** ([systemd meson_options.txt](https://github.com/systemd/systemd/blob/main/meson_options.txt); [systemd.kill(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html)). Those budgets are tuned for servers. An LLM session has to finish a tool call, commit its WIP to its own `agent/pse/<issue>-<slug>` branch, write its `SessionCheckpoint`, and release its lease, and that takes minutes. A grace window of **one scan (10 minutes)**, configurable per role, lets Jev's next scan check that the checkpoint landed and the lease was released. It also fits Claude Code's **600 s** default timeout for command hooks ([Claude Code: Hooks](https://code.claude.com/docs/en/hooks)). That hook surface is also the natural way to deliver the stop request between tool calls and to end the loop with a recorded `stopReason`. The cooperative step cannot be the whole design. Temporal delivers cancellation only to activities that heartbeat ([Temporal](https://docs.temporal.io/encyclopedia/detecting-activity-failures)), and a session stuck inside a long tool call likewise never sees a stop label. The hard stop, backed by lease expiry, is what guarantees the session actually stops.

### Leases need an epoch fence, not just a TTL

A lease TTL limits how long a dead holder can block others. An etcd lease "expires if the etcd cluster does not receive a keepAlive within a given TTL period", and its keys are deleted ([etcd Lease API](https://etcd.io/docs/v3.6/learning/api/#lease-api)). Releasing on graceful exit should be the normal path, as kube-controller-manager now does instead of waiting out the TTL ([Kubernetes: Leases](https://kubernetes.io/docs/concepts/architecture/leases/)). Neither mechanism stops a "stopped" session whose `git push` was still in flight. Kleppmann's fencing token covers that case: a number that increases with every grant, which the protected resource checks so that it rejects writes from older holders. His argument is cited here through secondary summaries ([Kleppmann 2016](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html), via [antirez](https://www.antirez.com/news/101)). The research could not confirm any conditional-write or If-Match support in Gitea's comment, label or branch APIs, so the fence should live in the coordination layer. One option fits Gitea well: the coordination service posts a lease-epoch commit status, and branch protection requires it through `enable_status_check` and `status_check_contexts` ([repo_branch.go](https://github.com/go-gitea/gitea/blob/v28.2.0/modules/structs/repo_branch.go)). Commits from a stale epoch can then never merge. The team's design source already says that lease expiry "must not automatically imply that another PSE may blindly continue in the same branch". Recovery checks the branch, commits, PR and last checkpoint first ([agent-engineering-team.md](../agent-engineering-team.md)). Anything already sent to the forge cannot be rolled back, so cleanup uses compensating steps: remove the in-progress label, mark the PR as draft, post one summary comment. Each step must be idempotent and able to resume, because "Compensating transactions are eventually consistent operations and can fail" ([Azure: Compensating Transaction pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)).

### Deterministic episode keys make every comment idempotent

Under at-least-once execution, a restarted Jev will retry and race with itself. Stripe's advice to use random v4 UUIDs as idempotency keys works for a client that keeps its key across retries ([Stripe: Idempotent requests](https://docs.stripe.com/api/idempotent_requests), secondary extract). A stateless monitor has to *derive* its key from the event instead: `hash(session_id, episode_id, level)`, so a fresh process regenerates the same key. Brandur Leach's recovery-point design supplies the rest ([brandur.org/idempotency-keys](https://brandur.org/idempotency-keys)). Jev records an intent row (key, recovery point) in its scan record *before* posting. It embeds the key as a marker in the comment body and stores the returned comment `id`. On retry, it finds its own comment by `user.login` plus the marker and `PATCH`es it rather than posting again. There should be one living status comment per episode per work item, not one per scan. One subtlety matters here: `since` filters on *update* time, so the stored `id` is the main lookup, and the full unpaginated list is the fallback after a crash. Escalation advances through recovery points (`detected → nudged → escalated_L1 → stop_requested → checkpoint_seen → stopped → escalated_L2 → resolved`), so a Jev that crashes halfway resumes without paging again. Dedup records should be kept for at least **72 hours**, Brandur's figure for surviving a Friday bug fixed on Monday. Stripe's 24-hour pruning window is too short for a human who answers after a weekend.

### Escalate when the Lead stays silent, not when Jev repeats itself

Alert fatigue comes from paging on the same thing again and again. The fix is to escalate when nobody acknowledges. PagerDuty's own on-call guide escalates a team alert "within 5 minutes" and relies on a backup on-call rather than asking one person to acknowledge everything ([PagerDuty: Being On-Call](https://response.pagerduty.com/oncall/being_oncall/)). Alertmanager groups related alerts into "a single compact notification", re-sends a notification only after `repeat_interval` (**4 h** by default), and uses inhibition to suppress hundreds of downstream alerts when a root-cause alert is firing ([Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/); [configuration](https://prometheus.io/docs/alerting/latest/configuration/)). For Jev, that becomes a three-level ladder. **L0** is the in-band nudge on the first bad scan. **L1**, on the stuck verdict, goes to the Lead, which may re-plan, reassign or authorise a stop. **L2**, a human, is paged only when L1 has not acknowledged within one scan or resolved within three. A human is also paged directly when OpenAI's two intervention triggers apply: a failure threshold has been exceeded, or the next step is high-risk or irreversible ([OpenAI practical guide](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf), via [secondary summary](https://cobusgreyling.substack.com/p/openai-ai-agent-design-guidance)). Alerts are grouped per work item. Per-session alerts are suppressed when a shared dependency is down: when every session's CI reads `pending` with zero statuses, the runner pool is the problem, and Jev raises one dependency alert in place of N stuck verdicts. Finally, the restart path needs a circuit breaker that only a person can reset. Azure's pattern recommends increasing open-timeouts and a "manual reset option" when recovery time is unpredictable ([Azure: Circuit Breaker](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker)). After two automatic restarts of the same work item, Jev parks it with `jev/parked` and escalates to L2. The count of two is a local choice; no source fixes it.

## Conclusion

The biggest change is not to any single threshold. It is the split between liveness, progress and repetition, which makes Jev's urgency uneven by design. Hung sessions cost nothing while they wait, so Jev can afford a slow, precise 30-to-40-minute path to a stuck verdict. Loops burn tokens on every iteration, so their detection belongs mainly inside the session. There, OpenHands-style counters or a Claude Code hook can nudge at the third identical failure, and Jev's role is to confirm and record. That division also keeps Jev read-mostly: the actor nearest the work catches the fast failure, and the watchdog with the least privilege catches the slow ones and keeps the evidence.

Two open items should go into the spec as `[NEEDS CLARIFICATION]` rather than be settled by default. The first is the 60-minute durable-progress window, which no source fixes, so it should be calibrated from Jev's first weeks of scan history per role (constitution Art. VIII). The second is where the epoch fence lives, since conditional writes in Gitea were not confirmed and the fence would otherwise sit in the coordination layer or a required status check. The Gitea findings were read from v28.2.0 source because the hosted docs were unreachable. Jev's start-up check should compare `/api/v1/version` and the instance's own `/swagger.v1.json` against these assumptions before it trusts any verdict.
