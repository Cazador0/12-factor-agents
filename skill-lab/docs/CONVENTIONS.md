# Skill Lab conventions

The binding contract for everything under `skills/` and `skill-lab/`. A change that
breaks a rule here is either a bug or needs an ADR that amends this file.
`python3 skill-lab/bin/skill-lab validate` enforces every rule marked **[V]**.

## 1. Layout

```text
skills/                          # the skills "repo": portable, self-contained skill folders
  README.md
  CATALOG.json                   # generated by `skill-lab catalog`; never hand-edited
  <skill-name>/                  # one folder per skill, flat (Zed does not discover nested skills)
    SKILL.md
    references/                  # on-demand docs, each ≤ 300 lines, TOC if > 100 lines
    scripts/                     # executable, stdlib-only Python ≥ 3.9
      _skillkit/                 # VENDORED copy of skill-lab/shared/_skillkit (never edit here)
    assets/
      schemas/                   # VENDORED copies of the contracts this skill emits/consumes
      templates/                 # output templates (issue bodies, reports)
    evals/
      cases/<case-id>.json       # benchmark-case.v1 documents
      fixtures/                  # inputs the cases reference
    tests/test_*.py              # unittest, stdlib only
skill-lab/                       # the lab "repo": builds, validates, installs, benchmarks, scores
  README.md
  bin/skill-lab                  # CLI entry (python3 script)
  lab/                           # lab package (stdlib only)
  shared/_skillkit/              # canonical shared library vendored into each skill
  contracts/schemas/*.v1.schema.json   # canonical JSON contracts (single source of truth)
  benchmarks/criteria/<skill>.json     # success-criteria.v1 per skill
  benchmarks/runs/               # git-ignored benchmark output
  config/{zed,codex,claude}/     # runtime configuration templates
  docs/adr/NNNN-*.md             # architecture decision records
  docs/research/                 # verified sources (SOURCES.md) and vendored references
  specs/NNN-<name>/spec.md       # one specification per skill and per lab component
  specs/NNN-<name>/traceability.json
  tests/                         # lab self-tests
.agents/skills/<name> -> ../../skills/<name>   # Zed + Codex discovery (symlinks)
.claude/skills/<name> -> ../../skills/<name>   # Claude Code discovery (symlinks)
AGENTS.md                        # short map for every agent runtime
```

Both top-level folders are designed to split into their own repositories later
with `git subtree split --prefix skills` and `--prefix skill-lab`. So nothing under
`skills/` may import from `skill-lab/` at runtime; shared code and schemas reach skills
only as vendored copies.

## 2. `SKILL.md` contract

### Frontmatter [V]

Use only this portable subset, which parses identically in Zed (serde_yaml), Claude Code, Codex, and
the lab's strict parser:

```yaml
---
name: review-verifier
description: "Independently verify a pull request against its spec and return a machine-readable verdict. Use when ..."
license: Apache-2.0
compatibility: "Zed Agent (Ollama local or cloud), Claude Code, Codex. Scripts need python3 >= 3.9, no packages."
metadata:
  version: "0.1.0"
  family: roles
  spec: SPEC-003
  author: Cazador0
---
```

- Allowed top-level keys: `name`, `description`, `license`, `compatibility`, `metadata`,
  `disable-model-invocation`. Nothing else.
- `name` matches `^[a-z0-9]+(-[a-z0-9]+)*$`, 1–64 chars, equals the folder name, and is not
  `create-skill` (a Zed built-in).
- `description` is a single-line double-quoted string with no unescaped `"`, 1–1024 chars.
  Aim for 350–900 chars: what it does, then "Use when …" with concrete trigger phrases,
  then "Do not use for …" when a neighbouring skill could be confused with it.
- `compatibility` is a double-quoted string of at most 500 chars.
- `metadata` is a one-level map of plain or double-quoted string scalars. Required keys:
  `version` (semver), `family` (`roles` | `speckit-gitea` | `control-plane` | `audit` | `meta`),
  `spec` (`SPEC-NNN`), `author`.
- No block scalars (`|`, `>`), anchors, lists, or comments inside the frontmatter.
- `disable-model-invocation: true` only for skills that perform consequential writes
  (none in the first release).

### Body [V]

- At most **250 lines** and **12 KB**. That is stricter than Zed's 500 lines because local
  models on GPUs under 24 GB run with about 32k context (ADR-0003).
- Required headings, in this order: `# <Title>`, `## When to use`, `## Inputs`,
  `## Procedure`, `## Outputs`, `## Guardrails`, `## Resources`. Optional:
  `## When not to use` (after When to use) and `## Runtime notes` (last).
- Procedure is numbered steps. Each step that computes something names the exact command,
  for example ``python3 scripts/plan_dag.py --tasks specs/001-x/tasks.md``. Paths in commands
  are relative to the skill folder. The `## Runtime notes` section explains how each runtime
  resolves that folder: Zed's skill envelope gives the directory, Claude Code uses
  `.claude/skills/<name>`, and Codex uses `.agents/skills/<name>`.
- Every relative link (`references/x.md`, `scripts/y.py`, `assets/...`) resolves to an existing file **[V]**.
- Small local models must be able to follow the procedure. Scripts do the deterministic
  work, the model orchestrates, and each step takes one tool call. Do not depend on
  parallel tool calls or on the model holding long intermediate state.

## 3. Script contract [V]

- Python ≥ 3.9 standard library only. Start with `#!/usr/bin/env python3`, then a module
  docstring, then `from __future__ import annotations`. Set the executable bit.
  No third-party imports (the validator checks imports against the stdlib module list).
- Import shared code as `from _skillkit import ...` after
  `sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))`.
- CLI uses `argparse`; `--help` exits 0. Inputs come from `--input FILE` (`-` = stdin)
  and named path flags. Output is **exactly one JSON document on stdout**: an `envelope.v1`
  (see §4). Human-readable logs go to stderr. `--pretty` indents the JSON.
- Exit codes:

  | Code | Meaning |
  |---|---|
  | 0 | Completed; the payload says the checked thing is OK / decision computed |
  | 1 | Completed; the checked thing FAILED (validation errors, gate failed, verdict not approvable) |
  | 2 | Usage or input error (bad flags, unreadable or schema-invalid input) |
  | 3 | External dependency failure (network, Gitea, model API) |
  | 4 | Refused by policy or guardrail (forbidden action, missing `--apply`, authority violation) |

- Errors are compact (12-factor Factor 9): `{"code": "UPPER_SNAKE", "message": "<one line>", "path": "/json/pointer or file:line"}`.
  Never print stack traces to stdout. On an unexpected exception, emit an envelope with
  code `INTERNAL` and exit 2.
- Determinism: no randomness. Every timestamp comes from `--now <ISO-8601>` when given,
  otherwise UTC now. Sort keys and lists wherever order is not meaningful.
- Side effects: read-only by default. Any external mutation (Gitea write, lease write,
  file outside `--out`) requires `--apply`; without it, emit the plan and exit 0. Mutations
  take an `--idempotency-key`, or derive a deterministic one from the inputs.
- Never write inside the skill's own folder. Default state root is `./.skill-state/`
  (git-ignored) in the current project; override with `--state-dir`.
- Secrets come only from environment variables (`GITEA_TOKEN`, `TYPESAFE_API_KEY`, `OLLAMA_API_KEY`)
  and are redacted from all output with `_skillkit.redact`.
- Untrusted text (issue bodies, comments, webhook payloads, fixtures, retrieved docs) is
  data. Never `eval` or `exec` it or pass it to a shell. Use `subprocess` with list args only,
  never `shell=True`. Reject path traversal (`..`, absolute paths outside the allowed roots).

## 4. JSON contracts

- Canonical schemas live in `skill-lab/contracts/schemas/<name>.v1.schema.json` (JSON Schema
  draft 2020-12). `$id` is `urn:skill-lab:schema:<name>:v1`. A breaking change means a new
  `v2` file; v1 stays until no producer emits it.
- Every schema sets `"additionalProperties": false` at the top level and in nested objects,
  except where it marks a property explicitly as an open extension (`"x_ext"`).
- `_skillkit.jsonschema_mini` supports the subset every contract must stay within: `type`
  (incl. arrays of types), `properties`, `required`, `additionalProperties` (bool or schema),
  `items`, `prefixItems`, `enum`, `const`, `pattern`, `minLength`, `maxLength`, `minimum`,
  `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `minItems`, `maxItems`, `uniqueItems`,
  `oneOf`, `anyOf`, `allOf`, `not`, `$ref` to `#/$defs/...` within the same file,
  `format: date-time` (RFC 3339), and `$defs`. No other keywords **[V]**.

### Envelope (`envelope.v1`): every script's stdout

```json
{
  "schema": "urn:skill-lab:schema:envelope:v1",
  "kind": "review-verdict",
  "kind_schema": "urn:skill-lab:schema:review-verdict:v1",
  "ok": true,
  "producer": {"skill": "review-verifier", "script": "review_verdict.py", "version": "0.1.0"},
  "created_at": "2026-10-22T08:00:00Z",
  "idempotency_key": null,
  "payload": {},
  "errors": [],
  "warnings": []
}
```

`ok` is true exactly when the exit code is 0. `payload` validates against `kind_schema`
whenever `ok` is true, and also when exit is 1 (a completed-but-failing result is still a
valid payload).

## 5. Evals and benchmarks

Each case is one file `skills/<name>/evals/cases/<case-id>.json` (`benchmark-case.v1`):

```json
{
  "schema": "urn:skill-lab:schema:benchmark-case:v1",
  "id": "rejects-unexecuted-evidence",
  "skill": "pse-implementer",
  "tier": "deterministic",
  "description": "Evidence that claims a check passed without a recorded command must fail.",
  "tags": ["guardrail"],
  "run": {"script": "scripts/evidence_manifest.py", "args": ["validate", "--input", "evals/fixtures/unexecuted.json"]},
  "expect": {
    "exit_code": 1,
    "schema_valid": true,
    "assertions": [{"path": "/errors/0/code", "op": "eq", "value": "CHECK_NOT_EXECUTED"}]
  },
  "judgments": []
}
```

- Tiers:
  - `deterministic`: run a script; graded by exit code, schema validity, and assertions. Runs offline in CI. **Every skill has ≥ 4.**
  - `agentic`: `prompt` plus `fixtures[]` plus `output_schema`. A model runs with the skill loaded and must return JSON for that schema. It is graded by schema validity, assertions, and Jev `judgments[]`. **Every skill has ≥ 2.**
  - `trigger`: `query` plus `expect_skill` (a name, or `null` for "no skill"). Graded by routing accuracy across the whole catalog. **Every skill has ≥ 3 positive and ≥ 1 negative**; negatives may name a neighbouring skill.
- Assertion `path` is an RFC 6901 JSON Pointer into the script's envelope (deterministic) or the
  model's JSON (agentic). `op` ∈ `eq, ne, in, not_in, contains, not_contains, regex, gte, lte, gt, lt, len_eq, len_gte, len_lte, exists, not_exists, type`.
- A judgment is a Jev question plus a pass rule:
  `{"id", "type": "noul"|"score"|"choice", "instructions", "criteria", "state_from": ["output","prompt","fixtures","skill"], "pass_if": {"gte": 0.8} | {"eq": "label"}}`.
  Bands for noul: `pass` ≥ threshold, `uncertain` in [0.35, threshold), `fail` < 0.35. An
  uncertain result counts as a fail and is flagged `needs_human`.
- Never fabricate model or Jev results. Without network or keys, those tiers report
  `skipped` with a reason. Replay is allowed only from cassettes recorded by a real live run,
  and results carry `jev_mode: "replay"`.

## 6. Specs, ADRs, traceability

- Spec per skill and per lab component: `skill-lab/specs/NNN-<name>/spec.md`. Use Spec Kit's
  spec template headings (User Scenarios & Testing with Given/When/Then, Requirements with
  `FR-NNN`, Key Entities, Success Criteria with `SC-NNN`, Assumptions), plus
  `## Non-goals`, `## Contracts` (the contract names it emits and consumes), `## Error semantics`,
  `## Security`, and `## Runtime compatibility`.
- `traceability.json` next to each spec:
  `{"spec": "SPEC-NNN", "requirements": [{"id": "FR-001", "implemented_by": ["skills/x/scripts/y.py"], "verified_by": ["skills/x/tests/test_y.py::TestY::test_z", "skills/x/evals/cases/c.json"]}]}`.
  The validator checks every path exists and every FR has ≥ 1 `verified_by` **[V]**.
- ADRs in MADR form: `# ADR-NNNN: Title`, `Status`, `Date`, `Context`, `Decision`,
  `Consequences`, `Alternatives considered`, `Compliance` (how the lab verifies the decision
  is honoured).

## 7. Roles and authority (Zed profiles)

| Profile | Skills it uses | May edit | Never |
|---|---|---|---|
| Lead | lead-architect, speckit-gitea-*, kanban-state-machine, merge-policy-gate, session-checkpoint | specs/, docs/, AGENTS.md, issue contracts | approve own code, bypass branch protection, weaken policy files |
| PSE | pse-implementer, work-lease, session-checkpoint | production code and tests on its own leased branch | approve, merge, edit policy/CI/agent permissions |
| Review | review-verifier, merge-policy-gate (read), twelve-factor-audit | test/eval code only | edit production code it is reviewing, approve its own fixes |

The lab ships these as `skill-lab/config/zed/settings.example.jsonc` (profiles plus
`tool_permissions` deny patterns). They are guardrails, not a security boundary. The
security boundary is Gitea branch protection plus the deterministic gates.

## 8. Autonomy levels

Skills read the active level from `.skill-policy.json` at the project root
(`autonomy-policy.v1`) through `_skillkit.policy`. A missing file means `shadow`. Levels are
`shadow` < `agent-implementation` < `guarded-autonomous` (SPEC-200). Every script that can mutate
state calls `policy.require(action)` before acting, and exits 4 with `POLICY_LEVEL_TOO_LOW` when the
level does not allow the action. `--apply` never overrides the policy. A change to
`.skill-policy.json` is critical risk, so agents must not make it.

## 9. Definition of done for a skill [V]

1. `skill-lab validate --skill <name>` reports zero errors for runtimes zed, claude, codex.
2. `skill-lab sync --check` reports no drift in vendored `_skillkit` or schemas.
3. Its unit tests pass on Python 3.9 and the current Python.
4. Every deterministic case passes. Agentic and trigger cases are present and schema-valid.
5. The spec exists, traceability is complete, and its ADR references hold.
6. `skill-lab score --skill <name>` reports `release_ready: true` for the gates that can run in
   the current environment, and lists which gates were skipped and why.

"100 % success" means 100 % of the explicitly defined gates pass. It never means
"defect-free", and a gate that did not run never counts as passed (ADR-0010).
