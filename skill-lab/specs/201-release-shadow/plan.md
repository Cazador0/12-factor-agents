# Implementation Plan: R1 Shadow mode

**Branch**: `release/r1-shadow` | **Date**: 2026-10-22 | **Spec**: [spec.md](spec.md) (SPEC-201)

**Input**: Feature specification from `skill-lab/specs/201-release-shadow/spec.md`, decisions in
[synthesis.md](synthesis.md), scope and gates in [release-plan.md](release-plan.md).

## Summary

Build the autonomy-policy core first: the `autonomy-policy.v1` file format, the 34-entry action catalog, and
`_skillkit.policy`, which loads fail-safe to `shadow`, clamps to the release maximum (`shadow`), and refuses
with exit 4. Then add four shared modules (`speckit_tasks`, `gitrepo`, `checks`, read-only `gitea`), a
read-only Gitea 28.x test double, and lab commands for policy, containment, release gates, and evidence
recording. Next comes `speckit-development` (User Story 2), which takes over execution of this `tasks.md` at
the self-hosting switch-over (T054). The 13 remaining skills follow as independent per-skill tracks,
each one spec → tests → scripts → SKILL.md → evals, grouped by user story; the 14th, `run-monitor` (SPEC-014),
gets its `snapshot.py` from SPEC-105. SPEC-105 (Jev live benchmarking) is delivered inside R1 by one umbrella
task (T150). Then the cloud-first Zed configuration, the standalone export, the offline gate run, the live smoke
run the person looks at, the live gate run that decides whether the R1 PR can merge, and the independent review
of the R1 PR. Every skill script whose action needs a level above `shadow` emits a plan without `--apply` and
exits 4 with it.

## Technical Context

**Language/Version**: Python ≥ 3.9 standard library only (CONVENTIONS §3). CI runs on 3.9 and the current CPython.

**Primary Dependencies**: none. The foundation `_skillkit` (envelope, cli, schemas, jsonschema_mini, ids, redact, fsutil, frontmatter, timeutil, assertions, jsonpointer) is vendored into every skill by `skill-lab sync`.

**Storage**: files. `.skill-policy.json` (project root, human-owned); `--state-dir` (default `./.skill-state/`, git-ignored) for leases, seen sets, check logs, and development state; `skill-lab/specs/201-release-shadow/evidence/` for committed evidence; `skill-lab/benchmarks/runs/<run_id>/` for live runs, committed with their results, run log, and health reports (SPEC-105 FR-015) and referenced from `evidence/live-runs.json` by digest, never copied.

**Testing**: `unittest` (stdlib) for unit, contract, and integration tests; `skill-lab bench` for deterministic, agentic, and trigger evals; the containment harness; Jev (TypeSafe System One) judgments for agentic cases, re-asked once when uncertain (SPEC-105 FR-002); fake TypeSafe and Ollama servers for every live-harness test (SPEC-105 FR-024).

**Target Platform**: Linux and macOS developer machines and Claude Code cloud containers. Runtimes: Zed Agent with Ollama Cloud (priority), Claude Code, Codex.

**Project Type**: portable skills plus a stdlib CLI lab.

**Performance Goals**: every skill script finishes in ≤ 2 s on the golden fixture on a developer laptop, so one procedure step stays one fast tool call for small models. The full deterministic suite finishes in ≤ 10 min in CI, so a PR gets feedback within one review cycle. These are targets, not release gates.

**Constraints**: offline-first; no structured outputs on Ollama Cloud (synthesis.md D-15); SKILL.md ≤ 250 lines and ≤ 12 KB (ADR-0003); no writes inside a skill folder (Zed cannot edit them, SOURCES.md); deterministic output with `--now`; secrets only from the environment.

**Scale/Scope**: 14 skills, 21 new and 6 changed contracts (plus SPEC-105's 2 new and 3 changed, delivered by T150), 5 new `_skillkit` modules, 8 new lab modules (plus 5 modified), 159 tasks. File-count estimate: about 860 files, of which about 365 are vendored `_skillkit` and schema copies generated by `skill-lab sync`. Per skill that is about 18 vendored modules, 6–10 schemas, 20+ eval cases (at least 4 deterministic, 5 agentic, and 10 trigger), 1–7 scripts, and 1–7 test files.

## Design details

### Policy module (`_skillkit/policy.py`, T017)

```python
LEVELS = ("shadow", "agent-implementation", "guarded-autonomous")   # rank = index
HUMAN_ONLY = "human-only"
SUPPORTED_MAX_LEVEL = "shadow"          # R1; SPEC-202 raises it after base-branch verification (D-3)
CATALOG_VERSION = "1.0.0"
POLICY_FILENAME = ".skill-policy.json"
MAX_POLICY_BYTES = 65536                # a deny list of all 34 ids is < 2 KiB; the bound rejects junk cheaply
class Action(NamedTuple): id; min_level; scope; risk; summary; introduced_in
ACTION_CATALOG: Mapping[str, Action]    # types.MappingProxyType, 34 entries (spec §Autonomy policy)
class Policy:                           # immutable; built only by load()
    level; declared_level; source; set_by; set_at; denied: frozenset; warnings: tuple
    def allows(self, action: str) -> bool
    def require(self, action: str) -> None          # raises envelope.ScriptError(..., exit_code=4)
    def refusals(self, actions: Iterable[str]) -> list      # one compact error per refused action, message starts with the action id
    def require_all(self, actions: Iterable[str]) -> None   # all-or-nothing preflight (FR-007): raises on the first refusal
def load(project_root: str, now=None) -> Policy     # never raises on content (FR-001/002)
def find_project_root(start: str) -> str            # nearest ancestor holding .git, else start
def catalog_document() -> dict                       # action-catalog.v1 payload
def state_document(policy, query=None) -> dict       # policy-state.v1 payload
```

Load algorithm: `os.lstat` → not a regular file ⇒ invalid; size > `MAX_POLICY_BYTES` ⇒ invalid; read bytes;
decode `utf-8-sig` ⇒ failure invalid; strict JSON (reuse `cli` duplicate-key hook) ⇒ failure invalid;
`jsonschema_mini.validate` against the vendored `autonomy-policy.v1` ⇒ failure invalid; every `deny` id in
the catalog ⇒ else invalid; clamp. Invalid ⇒ `Policy(level="shadow", warnings=(POLICY_FILE_INVALID,))`.
There is no `os.environ` access in the module. A static test greps for it.

### Wave rule (`_skillkit/speckit_tasks.py`, T019)

1. **Phase edges**: Foundational depends on all of Setup; every user-story phase depends on all of Foundational; Polish depends on every user-story phase; a `Convergence` phase has **no** phase edges. Its tasks fix already-built work, and a phase edge would deadlock it behind Polish tasks that wait on converge.
2. **Intra-phase order**: a task without `[P]` depends on the nearest preceding task in the same phase. A `[P]` task has no implicit intra-phase edge.
3. **Explicit edges**: every `(depends on T…)` id is an edge. An unknown id ⇒ warning `UNKNOWN_DEPENDENCY`, and the edge is unsatisfiable.
4. **Checked tasks** (`[x]`) are satisfied.
5. **Waves** are topological layers of unchecked tasks. Within a layer, two tasks whose write domains overlap are split (the later one by file order moves to the next layer) and recorded in `conflicts[]`. A task's write domain is the parent directory, plus `/**`, of every repository path in its description (golden: T006 and T007 share `src/auth/tokens/**`).
6. **Cycles** ⇒ `cycles[]` non-empty. Consumers refuse to execute (`TASK_GRAPH_CYCLE`).

Golden check: with T001 and T002 checked, wave 0 = `[T003, T004]` (T005 follows T004 by rule 2); T006 and
T007 land in different waves (rule 5).

### Check denylist (`_skillkit/checks.py`, T022)

Refused before any process starts (`CHECK_COMMAND_FORBIDDEN`, exit 4). Matching is on argv after unwrapping
`env VAR=… cmd`, `nice`, `timeout N`, and `nohup`:

- `git` with any subcommand outside `status, diff, log, show, rev-parse, ls-files, ls-tree, cat-file, merge-base, describe, for-each-ref, grep, apply --check`.
- forge and network CLIs: `gh`, `tea`, `glab`, `curl`, `wget`, `ssh`, `scp`, `sftp`, `rsync`, `nc`, `ncat`, `telnet`, `ftp`, `claude`, `codex`, `ollama`.
- opaque shells: `sh|bash|zsh|dash|ksh|fish` with `-c`, and `sudo`/`su`/`doas` with anything.

The child environment is the parent's minus every name in `redact.SECRET_ENV_VARS` (recorded in
`env_removed`). Default timeout is 600 s, overridable per check. The longest R1 check is the full lab test
suite, whose target is ≤ 10 min in CI, so 600 s fails a hung check without killing a healthy one.

### Gitea test double (`skill-lab/lab/gitea_double.py`, T024) and read client (`_skillkit/gitea.py`, T025)

The double binds `127.0.0.1:0` (ephemeral port), loads `skill-lab/fixtures/gitea-double/seed-golden.json`
(repo `acme/factory`, issues `T001: …`–`T003: …` plus one closed `T013: …` and one orphan `T099: stray`,
labels, one milestone, one PR with files), and serves:

| Method | Path (prefix `/api/v1`) | Notes |
|---|---|---|
| GET | `/version` | `{"version": "28.2.0"}` |
| GET | `/repos/{owner}/{repo}` | |
| GET | `/repos/{owner}/{repo}/issues?state=all&type=issues&page=&limit=` | paginated; total-count header per Gitea swagger, verified at T023 |
| GET | `/repos/{owner}/{repo}/issues/{index}`, `/comments`, `/dependencies`, `/blocks` | dependency endpoints per SOURCES.md |
| GET | `/repos/{owner}/{repo}/labels`, `/milestones` | |
| GET | `/repos/{owner}/{repo}/pulls/{index}`, `/pulls/{index}/files` | for merge-policy-gate inputs |
| GET | `/repos/{owner}/{repo}/branch_protections` | read only; the audit is R2 |
| GET | `/swagger.v1.json` | trimmed; no project-column paths ⇒ clients fall back to `state/*` labels (SOURCES.md) |
| any non-GET | any | **405** `{"message": "read-only test double (SPEC-201)"}`; always logged |

Every request is appended to `<log>.jsonl` as `{method, path, query, body_sha256, ts}`. The client's read
methods (`version`, `get_issue`, `list_issues`, `list_dependencies`, `list_labels`, `get_pull`,
`list_pull_files`, `list_comments`) follow pagination. A server version below 28.0.0 adds the warning
`GITEA_VERSION_UNTESTED`. `send(op)` calls `policy.require(op.action)` before opening a socket. In R1 it is
reached only by tests and always refuses. SPEC-202 extends both files with write endpoints and the ledger.

### Webhook defense layers (`normalize.py`, T103; T147–T149, T156)

The four layers the person chose ("All four layers in R1"; ADR-0107) keep three records under `--state-dir`,
each written only with `--apply` (action `state.write.local`):

| Record | Content | Rule |
|---|---|---|
| `events/seen.jsonl` | `{body_sha256, first_seen_at, delivery_id}` per verified body | A body whose SHA-256 is already listed is `duplicate: true`. The delivery id is metadata and never decides a duplicate. Entries older than 90 days are pruned on the next `--apply` |
| `events/objects.json` | per issue and per PR: the last processed signed `updated_at` and, for a PR, its head SHA, both read from the verified body, never from headers | A verified body with an earlier `updated_at`, or a PR body with the recorded `updated_at` and another head SHA, is `stale: true`, leaves the record unchanged, and drives no state change |
| `events/rate.json` | per object, the timestamps of verified bodies inside `--rate-window-s` (default 60) | Above `--max-events-per-object` (default 20) the delivery exits 4 `EVENT_RATE_LIMITED` and nothing is recorded |

Secret hygiene: a current or previous secret under 32 bytes exits 2 `WEBHOOK_SECRET_TOO_SHORT` before any
verification. `GITEA_WEBHOOK_SECRET_PREVIOUS` is tried only while `--now` is less than 7 days after
`GITEA_WEBHOOK_SECRET_ROTATED_AT` (warning `WEBHOOK_SECRET_PREVIOUS_USED`), and never without a rotation time. Both
secrets are in `redact.SECRET_ENV_VARS` (T022). A body that fails its signature is never parsed into output, logs,
or state: the exit-1 payload holds header values, configured values, and `body_sha256` only.
`references/webhook-hygiene.md` documents the ≥ 32-byte random secret, the TLS-only endpoint, and the rotation
procedure; creating the webhook stays `human-only`.

Events are hints (FR-047): `transition.py next|decide --event` and `dispatch_recommend.py --event` refuse to decide
without `--gitea-url` (`EVENT_REREAD_REQUIRED`, exit 2), re-read the issue, PR, reviews, and check status through
the read-only `_skillkit.gitea` client (the double in tests), and decide from that state alone. An unverified,
duplicate, or stale event decides nothing. R3 builds its live gateway on these layers and adds none of them.

<schema>` from the exported repo root, with tools restricted to read-only plus `python3 skill-lab/bin/skill-lab`.

verified with `claude --help` at T049 and recorded in `evidence/interface-notes.md`. The orchestrator posts
the resulting comment, which carries `reviewer.mode: cli-fallback`.

### Self-hosting switch-over (T054)

Before T054, the orchestrator executes tasks in `tasks.md` order using the wave rule above, writes tests
first, and from T022 on runs verifications through `_skillkit.checks`. At T054:

1. `dev_state.py status --feature skill-lab/specs/201-release-shadow` writes `evidence/development-report.json`.
2. For each checked task (T001–T053 and the Setup and Foundational tasks T144–T146), `dev_state.py check --task Tnnn --apply` re-runs its declared verification. A task with no passing `check-run` is unchecked again.
3. From then on, each task is closed only by `dev_state.py mark --task Tnnn --apply`, which requires a passing `check-run` for the task's declared verification.

**Verification derivation** (`dev_state.py check --apply`, action `state.write.local`): (a) each test path in the task description runs the way SPEC-101's `skill-lab test` runs its suite: a path under `skill-lab/tests/` (including `integration/` and `release/`, which therefore carry an `__init__.py`) becomes `python3 -m unittest discover -s <its directory> -t skill-lab -p <file>` from the repository root, because the lab tests import the `tests` package; a path under `skills/<name>/tests/` becomes `python3 -m unittest discover -s tests -p <file>` with the skill folder as cwd (`discover -s` works with hyphenated folders, which are not importable package names). This is the **test command convention** for every release spec: `python3 -m unittest <path>` written in a gate or an Independent Test line is shorthand for this form, and `gates.json` stores the full form; (b) each backticked command that follows the words "verify with" or "pass" in the description is split with `shlex` and run as is; (c) a task with neither, such as a doc-only task, needs at least one passing `check-run` attached with `mark --check-id <id>`, and the agent chooses that check (for example `skill-lab validate`). Every command still goes through the denylist and the env scrub.

## Benchmark plan (cloud-first)

The live gate run decides whether the R1 PR can merge (intake Q1, Q15; ADR-0106). R1 merges only after one fully
passing, counting live run.

1. **Prerequisites** (P-L): `OLLAMA_API_KEY`, `TYPESAFE_API_KEY` (or `JEV_API_KEY`); `ollama.com` and `api.typesafe.ai` reachable. Model M1 from `skill-lab/config/zed/cloud-models.json` (T112), one model for every case (SPEC-105 FR-001).
2. **Offline first** (T136): every offline merge gate passes before any live spend, so live spend is never wasted on a broken script.
3. **Smoke run** (T151; intake Q12): `python3 skill-lab/bin/skill-lab bench --tag smoke --runtime ollama-cloud --model <M1> --jev live --record skill-lab/benchmarks/cassettes` on the 3 smoke cases; the person looks at its report. A change to `skill-lab/benchmarks/monitor-limits.json` is proposed only with the measured normal levels and applied only after the person approves.
4. **Gate run** (T137): `python3 skill-lab/bin/skill-lab bench --tier agentic,trigger --runtime ollama-cloud --model <M1> --jev live`, writing to `skill-lab/benchmarks/runs/<run_id>/`. It runs to completion with no duration limit (SPEC-105 FR-004), logs every case, request, and health check to `run.log.jsonl`, and runs `run-monitor` after each skill (14 health reports, each with one advisory model call). Volume per run: at least 70 agentic cases (14 × 5, at most 2 repair turns each), at least 140 routing queries (14 × 10), about one Jev request per agentic case plus at most one re-ask per uncertain judgment, and 14 assessment calls.
5. **Score**: `skill-lab score --skill <name> --run <dir> --strict` for each skill and the catalog score (SPEC-105 FR-006), then `skill-lab streak` and `skill-lab report --run <dir>` (the PR comment of FR-038).
6. **Commit and record**: the run folder and the redacted cassettes are committed where they were written (SPEC-105 FR-015). `skill-lab release record-run --run <dir>` writes `evidence/live-runs.json` with the run id, path, sha256 of the run summary, model, `suite_digest`, `counts_toward_streak`, and the digest of the `benchmark-streak.v1` that includes the run. Nothing is copied into the evidence folder.
7. **Evaluate**: `skill-lab release check --spec SPEC-201 --stage merge` → `evidence/gate-report-merge.json`. Every gate, G-LIVE-01..12 included, must be `pass`; otherwise R1 does not merge.
8. **Counting rules** (SPEC-105): an uncertain judgment is re-asked once, then failed and flagged; a service failure after retries (connection error, HTTP 5xx, 429 after retries) makes the case `errored` and the run an `outage`, which does not count; 401, 403, and 422 are configuration or case bugs, not outages, but the case is still `errored`, so the run is incomplete; a run whose health check crossed a limit is `degraded` and does not count; a replayed run never counts. Cost comes from the person's `skill-lab/benchmarks/prices.json`, and a run with any missing price reports usage only. No spending cap stops a run (intake Q7).
9. **Without prerequisites**: every agentic and trigger case is `skipped` (`LIVE_PREREQ_MISSING`), every G-LIVE gate is `not_run`, and R1 does not merge. Nothing is fabricated or replayed in its place.
10. **On a failing live gate**: tune descriptions (trigger) or procedures and scripts (agentic), never thresholds. Criteria files, `gates.json`, and `monitor-limits.json` sit in critical policy paths; agents never edit criteria files or `monitor-limits.json`, and a threshold changes only with the person's approval, an ADR, and a human merge. Editing any `SKILL.md` or eval case changes the `suite_digest`, so the next gate run is required (`LIVE_RUN_STALE`).
11. **Streak bookkeeping for SPEC-202**: every live gate run is committed with its `benchmark-streak.v1`. SPEC-202's L1 entry is `local_unlock_evidence: true` for the cloud model (3 consecutive counting runs on the same model and suite digest) plus the person's recorded sign-off; a change of model, or editing or adding any case, starts a new streak.

## Rollout and rollback

- **Rollout in target projects**: `skill-lab install --project <dir>` creates the symlinks. No `.skill-policy.json` is needed; missing means `shadow`. The example policy is documentation only. Since R1 clamps to `shadow`, installing R1 cannot grant any agent a new remote capability.
- **Rollout of the factory repo**: live gate run passed and recorded → R1 PR → independent `APPROVE` from a reviewer holding no live keys → CI green → human merge = "R1 merged", which is also "R1 complete", because the live gates passed at the merge stage. There is no follow-up evidence PR.
- **Rollback in target projects**: remove the symlinks (`skill-lab install --uninstall`, or delete `.agents/skills/<name>` and `.claude/skills/<name>`) and delete `.skill-state/`. No remote state exists to undo, because shadow made no remote writes. Working-tree edits from `workspace.write` are uncommitted and revert with `git checkout -- <path>`.
- **Rollback of the factory repo**: a human reverts the merge commit on `main`. A regression found after merge goes in a new PR with its own review. SPEC-202 does not proceed past its entry check while R1 is reverted.
- **Feature flags**: none. The autonomy level is the flag, and R1 pins it at `shadow`.
