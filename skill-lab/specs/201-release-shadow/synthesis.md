## 1. Findings

### The report (governing design)

- **F-1 Three planes and the policy split.** Lead is the control plane, PSE the implementation plane, Review the independent assurance plane (report §Executive architecture). "The model may recommend actions; a deterministic policy engine decides whether the action is legal": "LLM decides what it believes should happen. Policy code decides what it is allowed to make happen. Gitea enforces the final repository rules" (report §Orchestrator state model). → `_skillkit.policy` is that policy code for skill scripts. Gitea branch protection plus human merge remains the enforcement layer.
- **F-2 Shadow mode definition.** "Lead, PSE, and Review analyze real work and produce plans/recommendations; humans perform consequential mutations" (report §Progressive autonomy). → R1 emits `gitea-plan`/`mutation-plan` and never writes remotely.
- **F-3 The authority invariant.** "Agents may operate autonomously inside the rules; they may not autonomously weaken the rules that define their authority." Changes to "the orchestrator, Gitea MCP server, CI policy, agent permissions, branch protection, secret-handling logic, and the Review agent's own gates" must not be self-authorized, and branch-policy changes are `critical` (report §Safe autonomous merge). → `policy.change` is `human-only`. The policy module, catalog, criteria, gates, CI, configs, and `skills/review-verifier/**` are critical paths for `merge-policy-gate`.
- **F-4 Mutation envelope.** "Every mutation should carry" `actor_role`, `session_id`, `issue_id`, `expected_version`, `idempotency_key`, `reason`, which guards against "an agent or retried event repeating a write after it has already succeeded" (report §Gitea as control plane). → `mutation-request.v1` (CONVENTIONS) gains a catalog-bound `action`.
- **F-5 Narrow semantic tool surface.** The recommended tools are named semantic operations (`gitea.issue.create`, `gitea.issue.dependencies.set`, `gitea.pr.enable_auto_merge`, `coordination.lease.claim`, ...). "Avoid an unrestricted `gitea.request(method, path, body)` tool" (report §Gitea as control plane). → The action catalog uses dotted semantic ids. The Gitea client has read methods plus one guarded `send()`, and no generic request method.
- **F-6 Kanban and transition function.** The report defines 10 states with owners and entry and exit conditions, `Blocked` as an exceptional status, and a deterministic `next_action(issue, project, pull_request, checks, review)` (report §Kanban state machine, §Orchestrator state model). → kanban-state-machine implements them verbatim.
- **F-7 Claiming work, leases, write sets.** The 8-step claim sequence; "A lease should have a TTL and heartbeat, but expiry must not automatically imply that another PSE may blindly continue"; branch format `agent/<role>/<issue>-<slug>`; a write-set estimate so that overlapping `expected_write_domains` are serialized (report §Claiming work safely, §Protecting against cross-agent conflicts). → work-lease overlap detection; lead write-set conflicts; takeover is R3.
- **F-8 Review independence.** Review "independently reconstructs expectations from the specification rather than accepting PSE's interpretation" and "should never silently repair the PSE's production implementation and then approve the combined result" (report §Review contract). → The requirements matrix is built from `spec.md`, and independence is a hard check.
- **F-9 Not run ≠ passed.** "the applicability decision itself must be explicit. 'Not run' must never silently mean 'passed.'" (report §Merge evidence gate). → quality gate, release gates, PR body.
- **F-10 Checkpoints are not chain-of-thought.** Persist "decision, rationale summary, evidence, assumption, tool result, changed state, unresolved question, next action" (report §Session checkpoint). → `session-checkpoint.v1` with `additionalProperties: false`.
- **F-11 Repository as memory, AGENTS.md as a short map.** `AGENTS.md` answers 8 questions only (report §Authoritative repository knowledge). → The export's AGENTS.md.
- **F-18 Measure accepted outcomes; promote autonomy on demonstrated reliability.** The core metrics table (first-pass approval rate, escaped defects, revert rate, unauthorized-action attempts blocked, ...), and "Promote autonomy only after the same workflow demonstrates reliability" (report §Core metrics, §Progressive autonomy). → Shadow mode should record what an autonomous decision *would* have been, so R3 promotion is evidence-based (`merge-decision.uncapped_decision`).

### Spec Kit

- **F-12 Spec Kit semantics.** `tasks.md` lines `- [ ] T001 [P] [US1] Description in path/file.py` with optional `(depends on T012, T013)`, task id regex `\bT\d{3,}\b`, phases Setup → Foundational → user stories → Polish (SOURCES.md Spec Kit). `implement` executes in dependency order. `analyze` is read-only. `converge` is "APPEND-ONLY, NEVER REWRITE": its only write is appending one `## Phase N: Convergence` section. "When the codebase already satisfies everything, the command MUST leave `tasks.md` byte-for-byte unchanged". Findings are classified `missing`/`partial`/`contradicts`/`unrequested` with severities CRITICAL/HIGH/MEDIUM/LOW, and "completion claims are not evidence" (`templates/commands/converge.md` @ `dc2cec4`). The `github` extension titles issues `T001: <description>` and deduplicates by the task-id regex across open and closed issues, and the core `taskstoissues` is deprecated (SOURCES.md; report §Gitea integration for Spec Kit). The checklist template is reviewer-owned, and `implement` treats checklist state as a gate.

### Runtimes and inference

- **F-13 Zed skills.** Flat discovery under `.agents/skills/`, symlinks supported; Zed reads only `name`, `description`, `disable-model-invocation`; `description` ≤ 1024 chars; catalog ≤ 50 KB (`MAX_SKILL_DESCRIPTIONS_SIZE`), with overflow dropped; the agent cannot edit `SKILL.md` or bundled resources; project skills load only from trusted worktrees; `create-skill` is built in; `agent.tool_permissions` uses regex patterns, and `always_deny` wins (SOURCES.md Zed).
- **F-14 Ollama.** Zed `language_models.ollama.api_url` is `http://localhost:11434` or `https://ollama.com`. Zed's default `num_ctx` is 4096; Ollama recommends ≥ 64000 for agents. Cloud auth is `Authorization: Bearer $OLLAMA_API_KEY`, and cloud models run at max context. **Ollama Cloud does not support structured outputs**; only local `/api/chat` accepts `format` (SOURCES.md Ollama).
- **F-15 Jev.** `POST {base}/v1/systemone`; env `TYPESAFE_API_KEY`, `TYPESAFE_BASE_URL`, `TYPESAFE_DEFAULT_MODEL` (`jev-latest`); question types `noul`/`choice`/`score`/`box`; HTTP 422 errors; "a noul near 0.5 means uncertain; typed output guarantees the interface, not truth" (SOURCES.md Jev). The user's alias `JEV_API_KEY` is already in `_skillkit.redact.SECRET_ENV_VARS`.
- **F-16 Claude Code and Codex.** Claude Code reads `.claude/skills/<name>/SKILL.md` and invokes `/name`. Codex scans `.agents/skills` from cwd up to the repo root, follows symlinks, and invokes `$name` (SOURCES.md). Spec Kit commands in Codex skills mode use `$speckit-*` (report §Spec Kit).

### Gitea

- **F-17 Gitea 28.x.** The current release is 28.2.0 (2026-10-18). REST is under `/api/v1`. Issue dependencies are `GET|POST|DELETE /repos/{owner}/{repo}/issues/{index}/dependencies` plus `/blocks`. Webhook headers are `X-Gitea-Event`, `X-Gitea-Delivery`, and `X-Gitea-Signature` (hex HMAC-SHA256 of the raw body). Project-column API coverage varies by version, so skills read `/swagger.v1.json` and fall back to exclusive scoped labels `state/<name>` (SOURCES.md Gitea). Gitea's API "exposes these as distinct operations": issues are closed, PRs are merged (report §Executive architecture).

### Factory environment and parallel work

- **F-19 Factory tooling (tool contracts observed in this environment, 2026-10-22; not in SOURCES.md).** `claude-code-remote` `create_session` takes `prompt`, `source_url`, `source_revision`, `title`, `tags`, and `permission_mode`. `permission_mode: plan` "BLOCKS waiting for human approval" and must not be used for an unattended child. "A session that finishes cleanly does not report back", so the parent polls `get_session` (`status_bucket`) and `list_events`. Commits from this build carry `Claude-Session: https://claude.ai/code/session_…` trailers. The user named the fallback `claude -p --output-format json --json-schema <review-verdict schema>`. The rest of the CLI surface (tool restriction flags, output wrapper field names) is verified at T049, not assumed.
- **F-20 SPEC-202 draft alignment.** R2 assumes the branch `release/r1-shadow`, reserves ADR-0201..0209, binds evidence to a `check-run.v1`, uses two exit states ("merged" / "complete"), builds the Gitea write path (double write endpoints, mutation ledger, live smoke), keeps the skills Gitea-only (the orchestrator does GitHub delivery), and records `mode: cli-fallback` on verdicts.
- **F-21 Foundation code present.** `_skillkit.envelope.ScriptError(code, message, path=None, exit_code=2)`, `ScriptResult`, `run_script`; `cli.read_json` is strict (duplicate keys rejected); `cli.read_text` uses `utf-8-sig`; `redact.SECRET_ENV_VARS` lists GITEA_TOKEN, TYPESAFE_API_KEY, JEV_API_KEY, OLLAMA_API_KEY, GITHUB_TOKEN, GH_TOKEN, ANTHROPIC_API_KEY, OPENAI_API_KEY; `ids.idempotency_key(*parts)`; `fsutil.safe_join` raises `PATH_TRAVERSAL` with exit 4.

## 2. Decisions

| ID | Decision | Rationale | Trade-off |
|---|---|---|---|
| **D-1** | `.skill-policy.json` governs **skill scripts acting on a target project**. Factory delivery to `Cazador0/skill-factory` (export, push, PR, reviewer session, verdict comment) is done by the build orchestrator under the user's explicit instruction and Claude Code's permission system, and the merge stays human | The user ordered the delivery process (SPEC-200), and the skills are Gitea-only (F-20). Conflating the two would either make R1's own PR impossible at `shadow` or require an escape hatch | The factory's GitHub writes are not catalog-gated; they rely on the orchestrator's permission prompts plus human merge |
| **D-2** | Fail-safe loading: missing → `shadow` with no warning; any unusable file → `shadow` plus one `POLICY_FILE_INVALID` warning; `load` never raises | A policy loader that can crash or escalate is itself an escalation path. `shadow` is the most restrictive level | A typo in a deny list silently disables the whole file, but it fails *towards* less authority and is visible as a warning in every envelope |
| **D-3** | Release clamp: effective = min(declared, `SUPPORTED_MAX_LEVEL`), and R1 ships `"shadow"`. Verifying the policy file against the protected base branch (so an uncommitted edit cannot raise the level) is deferred to R2, which must ship it before raising the clamp | In R1 the clamp makes the file content, `--project-root` spoofing, and uncommitted edits irrelevant to the effective level. In R2 they matter | R2 carries a hard prerequisite (recorded in cross-release dependencies) |
| **D-4** | `overrides` is restrict-only: `{"deny": [action ids]}`. There is no allow list, no per-skill override, no `x_ext`, and no expiry field. An unknown deny id makes the file invalid | Deny-only overrides let a human run a level minus specific actions (for example a merge freeze during an incident in R3) without creating a way to grant authority. An expiry (auto-demotion) is useful but belongs with R3's promotion and demotion machinery | Fine-grained elevation is impossible by design. Elevation is always a whole-level change by a human |
| **D-5** | The catalog lives in code (`_skillkit/policy.py` `ACTION_CATALOG`), is vendored with the module, and is emitted as `action-catalog.v1`. It holds all 34 ids, including every R2 action and the 7 guarded R3 actions, now. A pseudo-level `human-only` marks actions no agent level allows | A code constant travels with the vendored module and is drift-checked by `sync --check`. A data file would need a loader and a precedence rule. Defining future actions now means R2 changes enforcement, not vocabulary, and R1's refusal tests already cover R2's and R3's guarded actions | Adding an action later still needs a catalog version bump and a critical-path PR. SPEC-203 does exactly that for two restrict-only ids (`autonomy.demote`, `gitea.pr.merge_schedule.cancel`; catalog 1.1.0) and lowers nothing |
| **D-6** | Three local actions are allowed at `shadow` (with `--apply`): `state.write.local` (including check logs), `workspace.write`, `review.local.run`. Everything that writes git history, a remote, or the forge needs `agent-implementation` or more | They change nothing outside the operator's machine, and the partition table puts local leases, local checkpoints, local task execution, and local file scaffolding in R1. CONVENTIONS still requires `--apply` for them | `workspace.write` lets a skill edit `tasks.md` or scaffold files at `shadow`. Those are uncommitted, reviewable diffs |
| **D-7** | All-or-nothing preflight: `require()` every action of a plan before the first side effect. A refusal envelope never carries the plan | A multi-step plan must not half-apply. Keeping "refused" (exit 4) and "planned" (exit 0) disjoint makes containment measurable | Callers re-run without `--apply` to see the plan |
| **D-8** | `run_check` strips `SECRET_ENV_VARS` from children and refuses a denylist (git write subcommands, forge and network CLIs, `sh -c`-style wrappers) before starting a process | Local checks are allowed at `shadow` because "it changes nothing external". Without tokens, a check cannot call a forge API on the operator's behalf | A denylist is a guardrail; arbitrary interpreters (`python3`) can still do anything the OS allows (R-1) |
| **D-9** | R1 owns the **read** path: `_skillkit/gitea.py` (GET methods plus a guarded `send()` that always calls `require()`) and a loopback read-only double that logs every request and answers non-GET with 405. R2 owns the write path (double write endpoints, mutation ledger, live smoke) | Shadow mode analyzes real work, which needs reads. The request log makes "0 non-GET requests" observable for containment. Splitting by read/write avoids duplicate work with SPEC-202 (F-20) | Skills' deterministic evals use file inputs, not HTTP; only integration and containment tests start the double |
| **D-10** | Five modules go into canonical `_skillkit`: `policy`, `speckit_tasks`, `gitrepo`, `checks`, `gitea`. Skills receive vendored copies | Four skills parse `tasks.md` (lead, taskstoissues, sync, speckit-development), three run checks (pse, speckit-development, review), and four read git (pse, review, checkpoint, speckit-development). Duplicated parsers drift. Vendoring keeps skills self-contained (CONVENTIONS §1) | `_skillkit` grows by five modules. Each is unit-tested once in the lab and drift-checked in every skill by `sync --check` |
| **D-11** | `speckit-development` is User Story 2 (P1), built right after the policy core, followed by a **self-hosting switch-over** (T054). Before T054 the orchestrator follows Spec Kit implement semantics by hand; at T054 the earlier tasks' verifications are re-run with `dev_state.py check --apply` | The user asked for `/speckit-development` as the execution command (SPEC-200 step 5). Building it first lets it deliver ~60 % of R1's tasks and makes RG-5 a measurement rather than a claim | Building the delivery tool inside the release it delivers is a bootstrap; the backfill step keeps the evidence honest |
| **D-12** | Review loop: `review-request.v1` (deterministic `request_id`, head SHA, round ≤ 3, exact commands); a verdict comment = one marker line plus one fenced `json` block holding `review-verdict.v1`; a **fresh reviewer session per round**; acceptance requires `request_id` match, `reviewed_commit` = head, reviewer session ≠ author session, and the reviewer session absent from every `Claude-Session:` trailer in `base..head`. In R1 the enforcement point is the human merge, not a GitHub Actions status check | Identity alone proves nothing: both sides may post as the same GitHub account (R-4). Session ids and commit trailers are machine-checkable. A fresh session per round prevents anchoring on its own earlier verdict, while prior verdicts stay readable on the PR. 3 rounds bounds the loop. Repeated rejection signals spec ambiguity, which goes to the human (report: Lead arbitration, escalations per accepted issue) | Each round costs a new session. An Actions-based verdict check would need workflow permissions and a trusted bot identity, so it is left to a later release |
| **D-13** | The `claude -p` fallback ships in R1 as **read-only** (`review.local.run`, allowed at `shadow`): it returns the verdict on stdout and posts nothing | Refines the partition (which listed the fallback in R2). The roadmap requires the review loop to work on the R1 PR itself, and the fallback is the only path when `create_session` is unavailable. A read-only process changes no shared state, the same category as `run_check` | CLI-launched review is weaker independence (same principal launches it); the verdict records `reviewer.mode: cli-fallback`, aligned with SPEC-202 |
| **D-14** | Cloud-first: every Zed profile (Lead, PSE, Review) defaults to **one** primary Ollama Cloud model M1 in R1. The local profile ships as `local-ollama.disabled.jsonc`, and `skill-lab install --inference local` refuses with `LOCAL_INFERENCE_GATED`. Model ids are taken from the live service at T112 and recorded in SOURCES.md with the date | One model means fewer variables and a cheaper 3-run streak for SPEC-202's L1 gate, and makes local-vs-cloud comparable. Model names are not in SOURCES.md, so they are not invented here | Per-role model specialisation (for example a coder model for PSE) is deferred until benchmark data shows a need (Q2) |
| **D-15** | No skill depends on structured outputs. Scripts produce every JSON payload, and the model orchestrates and relays. Agentic cases embed `output_schema` in the prompt and are validated after the fact | Ollama Cloud has no structured outputs (F-14), and the priority runtime is Zed + Ollama Cloud | Agentic JSON validity is a measured risk (RK-3), not a guarantee |
| **D-16** | Gates have a class (offline/live) and a stage (`merge`/`complete`/`post-review`). There are two exit states, "merged" and "complete" (same as SPEC-202). A live gate that ran and failed blocks the merge; `not_run` makes R1 "merged, live-pending". Thresholds: deterministic 100 %; agentic ≤ 1 failed case per skill (`bench.agentic.failed`) and guardrail 1.0; trigger ≤ 1 failed (misrouted) case per skill (`bench.trigger.failed`) and ≥ 0.90 catalog-wide (≥ 78 cases; ≤ 7 misses, so per-skill tolerance cannot compound); 1 complete live run. The per-skill criteria files replace SPEC-104's optional rate defaults by id so `skill-lab score` agrees with these gates (spec.md §Release gates) | Deterministic scripts admit no failure. Capability under model nondeterminism tolerates exactly one miss per skill. A count says that at any case count, while a rate does not: the first draft's "agentic ≥ 0.67" rejected 2/3 = 0.667 (found by SPEC-203 X-2). Invariants tolerate none. One run is a baseline; reliability is SPEC-202's 3-run L1 gate. "Not run" never counts as pass (F-9) | Small per-skill samples make any per-skill gate coarse. The catalog-wide gate compensates |
| **D-17** | Evidence produced up to T139 is committed under `specs/201-release-shadow/evidence/` (redacted run summaries and cassettes included; raw runs stay git-ignored). Evidence produced at or after the reviewed head (PR record, review request, verdict, post-review report) is **not** committed to the R1 branch; it lives in the PR thread and in R2's entry check | Committing after review moves the head and invalidates the verdict (`VERDICT_STALE`) | The R1 branch alone does not contain its own verdict. The PR thread does |
| **D-18** | Export: a lab script assembles a fresh tree (no 12-factor-agents history). LICENSE is copied byte-identical, plus a NOTICE for MIT-vendored files and the upstream concept attribution. Only `skills/`, `skill-lab/`, and templated root files are included, with 26 relative symlinks. The manifest lists every file except itself, and its digest excludes timestamps. The script performs no git operations | Standalone and reproducible; a reviewer can verify the tree against the manifest without the source repository. Git operations are factory delivery (D-1) | History of the skills before export is not carried into the factory repo |
| **D-19** | `twelve-factor-audit` references paraphrase the 12 factors and link to upstream; nothing from `content/` is copied | Upstream content is CC BY-SA 4.0 (F-22). Copying it would put a share-alike licence on Apache-2.0 skill files | Users must follow the link for the original wording |
| **D-20** | Eval counts above CONVENTIONS minimums: ≥ 3 agentic (≥ 1 `guardrail`) and ≥ 4 positive plus ≥ 2 negative trigger cases per skill (≥ 1 negative naming a neighbour, ≥ 1 expecting `null`), plus 1 `policy`-tagged deterministic refusal case per (skill, action above `shadow`) | With 2 agentic cases a per-skill threshold can only be 0.5 or 1.0. A single negative cannot separate neighbour confusion (taskstoissues/sync, lead/speckit-development, kanban/merge-gate) from over-triggering on generic queries | ~50 % more eval authoring than the minimum |
| **D-21** | Contract changes in R1 are additive and stay v1: optional fields only, plus `implementation-evidence.head_commit` widened to nullable. No v2 files | Every producer and consumer is in this repository and re-vendored in the same release. CONVENTIONS reserves v2 for breaking changes | Old consumers would reject new optional fields (`additionalProperties: false`); `sync --check` makes that impossible inside the repo |
| **D-22** | ADR numbers 0101–0109 for R1 | SPEC-202 reserved 0201–0209; the foundation uses 00NN | A release-scoped block is unusual for MADR but prevents parallel-planner collisions |
| **D-23** | Layered policy-file protection: Zed `tool_permissions` always-deny for `edit_file` on `.skill-policy.json` and for terminal commands that mention it; Claude Code `permissions.deny` Edit/Write rules (syntax verified at T038); `merge-policy-gate` classifies the file `critical`. Codex has no per-path deny in SOURCES.md, so there it is AGENTS.md instruction plus merge gate | Guardrails, not a boundary (CONVENTIONS §7). The boundary is the protected branch plus human merge | Codex coverage is weaker until a per-path control is verified |
| **D-24** | `merge-decision.v1` gains optional `autonomy_level` and `uncapped_decision`. The decision itself never exceeds what the level allows (`HUMAN_APPROVAL_REQUIRED` cap below `guarded-autonomous`) | Shadow mode exists to collect evidence for promotion (F-18). Comparing `uncapped_decision` with what humans actually did yields a calibration record for R3 | Consumers must not act on `uncapped_decision`; the spec and SKILL.md say so |
| **D-25** | Partition refinements: (a) the read-only `claude -p` fallback moves to R1 (D-13); (b) `speckit-gitea-sync` produces its comment plan in R1, with apply in R2; (c) `merge-policy-gate` records `uncapped_decision` (D-24); (d) `run_check` scrubs secrets and denylists commands (D-8); (e) review-verifier's independence check uses commit trailers (D-12); (f) lead's dispatch recommendation carries the exact `mutation-request` items R2 will apply; (g) `delivery_plan.py` (pse and speckit-development) takes `--step` so each catalog action is planned and refused individually (one tool call per step for small models) | Each refinement keeps the level semantics: nothing consequential happens before R2 | None changes a level boundary |

## 3. Trade-offs considered and rejected

| Alternative | Why rejected |
|---|---|
| Environment variable `SKILL_POLICY_LEVEL` for CI convenience | Agents can set environment variables; it would be an escape hatch (F-3) |
| Treat a malformed policy file as an error (exit 2) | Breaks every script on a typo and invites "fix by deleting the file", which yields `shadow` anyway. Fail-safe-with-warning is simpler and strictly safer |
| Catalog as a JSON data file in `contracts/` | Needs a runtime loader and a precedence story; a code constant is vendored and drift-checked by the existing sync mechanism |
| Reuse one reviewer session across rounds via `send_message` | Anchoring on its own earlier verdict; and per F-19 a cloud session cannot message back, so the orchestrator would poll anyway |
| Live gates block the merge even when `not_run` | Makes the merge wait on the network allowlist with no added safety. SPEC-202 adopted the same two-state model |
| No Gitea HTTP code at all in R1 (file inputs only) | Containment would be "trivially" true and unobservable, and shadow mode could not read real work |
| One contract per skill output reused across skills (for example overloading `implementation-evidence` for patches) | Overloading hides semantics; every payload must validate against its own `kind_schema` (CONVENTIONS §4) |
